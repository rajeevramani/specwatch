# Ablation variants

Generated by `../ablate.ts` (task specwatch-sl1). Each variant takes the gold
spec (`../specs/gold.yaml`) and degrades **exactly one** phase-1 JAIRF signal
family, so a downstream task-success drop is cleanly attributable to that signal.

Regenerate:

```sh
cd ../backend
npm run ablate          # writes *.yaml + manifest.json here
npm run lint:variants   # OpenAPI 3.1 structural validity (needs network for npx)
npx vitest run test/ablate.test.ts   # single-signal-diff + manifest-score assertions
```

## Variants

| File | Degrades | Signal family | How |
|---|---|---|---|
| `gold.yaml` | nothing | — | copy of the baseline |
| `no-descriptions.yaml` | descriptions | `description_coverage`, `doc_clarity`, `descriptive_richness` | strip descriptions from operations, parameters, request bodies, all schemas, response headers, tags (response-object descriptions are kept — required by OpenAPI 3.1) |
| `bad-operationids.yaml` | operationId | `operationid_quality`, `distinctiveness`, `tool_calling` | drop a third of `operationId`s, snake-case some, force duplicates |
| `no-examples.yaml` | examples | `request_examples`, `response_examples` | strip every `example`/`examples` |
| `no-error-schemas.yaml` | errorSchemas | `error_standardization`, `type_specificity` | demote error bodies from `application/problem+json` (with the `Problem` schema) to a plain `application/json` body with no problem-details schema |
| `thin-responses.yaml` | completeness | *(runtime-driven — no static signal)* | **identical to gold** — see below |
| `all-bad.yaml` | all of the above | many | every spec-level degradation at once |

## Response completeness is a runtime signal

The `–completeness` ablation is **not** a spec edit. JAIRF response completeness
measures whether write endpoints actually return the full created/updated
resource — something a static spec read cannot tell you (the gold spec documents
complete bodies regardless of what the server sends). It is grounded only from
observed traffic.

So `thin-responses.yaml` is byte-identical to `gold.yaml`. The degradation is
applied at **run time** by starting the calibration backend with the
`THIN_RESPONSES=1` toggle (see `../backend`), which makes write responses return
thin (id-only) bodies. The agent runner pairs this gold-equivalent spec with the
thin-response backend; Specwatch then observes the low completeness. The manifest
marks this variant `"runtimeDriven": true` and `all-bad` lists `completeness`
among its degradations because the all-bad run is expected to use the toggle too.

## `manifest.json`

Machine-readable index consumed by the analysis task (specwatch-51h). Per
variant: the signal family/families degraded, `runtimeDriven`, the relative spec
path, and the JAIRF score AgentReady computes for it — overall/grade/level,
per-category scores, and the full per-signal breakdown.
